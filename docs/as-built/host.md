# The Rust host as built

The four services in `crates/host` — what each owns, and the rules a later phase must not undo. The rules here are binding; `CLAUDE.md` points here instead of carrying them.

## The Rust host as built (P4–P6)

`crates/host` is a Cargo workspace member and a plain library — a test asserts zero `tauri::` imports over the whole `src` tree, and **P6 kept it that way**: Tauri lives in `crates/app`, which depends on the host and is depended on by nothing. Four services live in the host, and they compose without knowing about each other:

```text
FlagService::freeze()  →  CatalogService::build_snapshot()  →  MatchService::play_load()
                                                                        ↓
                                                          CatalogService::play_persist()
```

Module map (`crates/host/src/`): `service` (the §13 command surface, the only writer of a Play) → `play` (the materialized projection, a pure fold) → `event` (the append-only log) → `ring` · `session` · `timer` · `award` · `rules` · `snapshot` · `settings` · `stage`; `flags` (`FlagService`); `catalog/` (`service` · `model` · `snapshot` · `store` · `search` · `db` · `error`); `presentation` (`PresentationService`) · `monitor` (where the Stage window stands) · `notice` (the §14 shape).

Rules a later phase must not accidentally undo:

- **No clock inside the host.** Every command — catalog writes included — takes `now_ms`; a running timer is `remaining as of running_since`. A tick never mutates a Play: `tick` only applies the T=0 table, and it applies it at the *computed* zero instant, so poll cadence cannot change a score and a replay lands on the same millisecond. P6 emits every 100ms by **reading** `stage::project`.
- **The log only grows.** Undo appends `TurnInverted { target_event_id, from_seq, to_seq }` and the projection is rebuilt; redo appends `TurnReapplied` and is legal only while the undo is still the last event. `events` is append-only in SQLite too, and the `plays` table is a projection rebuilt from it at `CatalogService::open`.
- **`FrozenSettings` live in `PlaySnapshot`, `LiveSettings` on the service.** There is no command that writes a frozen key — that is how §2.5 is enforced, not by disabling a control. `FlagService::settings_set_current_game` refuses a game-affecting key while a Play is open, and `play_load` re-validates the snapshot's settings against the §4.2 interlocks in case the row came from an older build.
- **`stage::project` emits the game half of `PlayStateForStage`**; `currentScreen`, `overlay`, `revealModes` and `decor` are `PresentationService::play_state`'s to merge (`revealModes` comes from `FlagService::reveal_modes`, never a second store). Keep the split: the 100ms tick re-projects the game half and must not touch the queue. `crates/host/tests/stage_contract.rs` checks both the half and the whole emission against every `fixtures/*.json`, so bump `stage::CONTRACT_VERSION` and `packages/contract` together.
- **`give_token` is refused while a question is issued and unrevealed**, in both `override.after_lock` modes; the setting decides the Control affordance (`FlagService::show_give_token`), and `allow` pairs with `reveal_and_pass` (§2.6 path 2).

## `PresentationService` (P6)

What the operator has chosen to show: the **current screen**, the **overlay queue**, and the recipe's **decor settings**. Everything else it appears to own it borrows.

- **Reveals are Play state.** `reveal_stem`, `reveal_next_option` and `reveal_leaderboard_rank` take `&mut MatchService` and delegate. There is no way to spell a second writer.
- **`revealModes` and `overlay_animations.enabled` are passed in per call**, from `FlagService`. A stored copy is the drift §2.16 forbids — the same discipline that keeps `play.status` out of `FlagService`.
- **The queue advances on an ack, never on a clock** (§2.6): one active, at most one pending, a newer pending replacing an older. `anim_complete(key, …)` is the single door for Stage's handshake; an unmatched key advances nothing and is not an error, because Stage reports *every* timeline it plays.
- **Overlays are enqueued from a diff of the projection** (`observe(prev, next)`), not from the command: §5.6 says a kind is enqueued when its **cause** occurs, and the same cause arrives from a resolve, an override and an undo. `current-team` has no automatic cause of its own; it stays operator-called.
- **The queue counts occurrences, not values** (`StageOverlay.run_id`, contract v5). Two identical requests are two runs: `round-advance` on the same round, or the operator pressing one overlay button twice, produce an `active` equal by value to the run that just finished. Keyed on the value, Stage saw "still the same run", played nothing, acked nothing — and since the queue advances only on an ack, every overlay for the rest of the Play sat in `pending` (2026-09-07). `run_id` is bumped in `run()`, the one place a request goes on air, and `OverlayLayer` keys on it.
- **Auto reveal chains host-side.** A beat is an append, so Stage driving it would be a second writer. `reveal.outcome` has no chained command — the outcome node appears as part of `reveal_outcome`, the only thing that scores.
- `show_screen` refuses everything but Idle before `play_start`: nothing else has a roster, a board or a score to draw.

## Stage on several displays (P11.11)

One **pacer** and N **mirrors**. `stage` is the pacer — created on first Control Load, alive until the app quits — and `stage-2`, `stage-3`, … are mirrors, created with **`?mirror`** on the URL the way the Viewer uses `?viewer`, so a window knows what it is *synchronously* on its first render rather than after an async label fetch.

- **A mirror differs in exactly two behaviours, and both are load-bearing.** It mounts `silentAudio` — every Stage window playing every cue is a flam, and the OS mixes them to one device anyway. And it does not acknowledge an animation: `overlay_ack_complete` returns early unless the caller is `guard::STAGE`, because two displays play the same timeline and the second ack would retire an overlay the operator has not seen finish, or promote a pending one twice. Dropped rather than refused — the mirror is behaving correctly, and a notice would be noise during a show.
- **The pacer is never promoted or demoted.** Its display unplugged pulls it back to primary and it stays the pacer (§9, unchanged). Who paces the show must not be a moving target mid-show.
- **`StageDisplay::live_mirrors()` is the whole contract with the app crate**: which connected displays should carry a mirror *right now*. `windows::reconcile_mirrors` makes the windows match — declarative, not a diff of opens and closes, so the monitor watch can call it on every display change without remembering what it did last time, and a missed close cannot leave a window on a display that is gone. It runs **after** `apply`, so a mirror is never opened on the display the pacer is about to move onto.
- **One pane per display, both ways round.** Adding a mirror on the pacer's display is refused (`MonitorError::AlreadyShowingStage`); sending the pacer to a mirrored display retires that mirror.
- **`stage_mirror_ids` sits beside `stage_monitor_id`**, which keeps meaning "where the pacer goes". No settings migration, and every `monitor.rs` test from P6 passes unchanged — which is the check that single-display behaviour did not move.
- **`guard::is_stage_label` is shared with `emit`.** A window the guard admits but the emission loop skips is a black screen on an audience display, so there is one predicate.
- **`writesSettings` in `host/commands.ts` must name every settings-writing command.** The settings document has no host event of its own, so a write is the one moment Studio knows to re-read it; a command missing from that list looks like it did nothing, and the control the operator just used springs back.
- **`ensure_stage` takes where Stage belongs, and it is not optional.** Forgetting it was a bug that lasted from P6 to P11.11 and could not correct itself: the monitor watch runs before Control Load, sees the remembered display connected, sets `on` and returns a move; `apply` finds no window and does nothing; Control Load builds the window fullscreen on primary asking nothing; and every later tick sees `on` already claimed, so no move is ever returned again. Stage then sits on primary for the whole show while the host insists it is elsewhere. **Place the window at birth** — that is what makes the claim true the moment there is something to claim.
- **`stageOn` is the *place*; `control.stage_monitor_id` is the *pick*.** They differ more often than they look like they should — a remembered display unplugged, a window not yet created — and Studio reading the pick where the place was meant is the other half of the same bug. `monitors-changed` carries `stageOn` **resolved** (the primary display's own key, never `null`, when Stage is on primary) plus `stageOpen`, because `null` meaning both "on primary" and "no window" is what made a card go blank while the show was on it. `chrome/windows.ts` holds both, beside `statsOpen`: window state, not settings state.
- **`monitors_list` reports connected displays and nothing else**, so a `MonitorCard` drawn from that list may never carry the `remembered` state — it renders as a dashed warning border reading *Not connected*, and saying that of a display sitting right there sends the operator hunting a cable fault that does not exist. A remembered display Stage is not standing on is `free`: it offers *Send Stage here*, which is what the operator wants from it, and the "Remembered:" line under the cards is where the pick is reported.
- **Every window label must match a capability, and the match is a glob.** A webview whose label matches none gets **no core permissions at all**, silently: it builds, it renders, it can still call this app's own commands (`generate_handler!` registers those for every webview, which is why `guard::allow` exists) — but `listen` is denied, so it never receives `play-state` or `play-tick` and draws `EMPTY_PLAY_STATE`, the Idle screen, for the whole show. `audience.json` is scoped `["stage", "stage-*"]` and `statistics.json` covers `stats`, which had never had one. `crates/app/tests/capabilities.rs` enumerates every label `windows.rs` can create and fails if one is uncovered — the log's tell was `stage_ready` twenty-two times from `stage` and zero from `stage-2`, because that call sits after `listen` in the same block.
- **P11.6 is load-bearing here.** Three displays are three different CSS viewports — 1920×1080, 1366×768, 1280×720 on the operator's desk — and `StageFit` is the only reason the same canvas lands correctly on all of them.
- **Each extra display costs about one renderer** (~11% of a core, ~100–150 MB, mostly its own decor world). The wire cost is negligible after P11.9.

## `monitor` — where Stage stands (P6, §9)

**The host never picks a display.** Stage is *ready*: fullscreen on primary from first Control Load, waiting. The first send is manual and is remembered in `stage.monitor_id`; a remembered display that reappears is taken automatically **outside** a Play, and mid-Play `stage.reattach` (`ask` | `auto` | `stay`, default `ask`) decides. Unplugging pulls the window back to primary with a warn notice and **does not touch the Play** — nothing in this module can reach one. Two identical panels collide on one key, and that case asks rather than guessing.

The OS list arrives as `Vec<MonitorInfo>` in **logical** pixels; that parameter *is* the monitor seam, and an unplug test needs nothing more than a shorter vector. Do not add a trait for it.

## `FlagService` (P5)

The §4.2 document and the only flag reader. It holds the globals, the recipe in Control, and the live control-behaviour copy — and **never** `play.status`, `session.locked` or `overlay.busy`: those arrive as a `RuntimeContext` built from `MatchService` at the call site, because a stored copy is exactly the drift §2.16 forbids.

- Every write lands on a **clone**, the clone is validated whole, and only a legal document is committed. A refused write changes nothing.
- The interlocks live on the settings types (`ScoringSettings::validate`, `TurnSettings::validate`, `TimerLevel::validate`), so `FlagService` and `MatchService::play_load` run the same table.
- `feat.*` is a **graph**: a child root is off whenever an ancestor is, whatever its own switch says. `require_feature` is the `feature_off` gate.
- `disabled(ctx)` returns every key that is frozen, inert or feature-off, with the reason — §4.2's "UI disables the illegal sibling first", computed once here rather than four times in Studio.
- `reveal.*` is the one Game-tab key that does **not** freeze: §4.2 lists it as a Game default *and* Control live.

## `CatalogService` (P5)

`rusqlite` with `bundled`, WAL + `synchronous = FULL`, one writer connection behind a `Mutex`, handwritten forward-only migrations on `user_version`. The interface never hands a `Connection` out, and `catalog/store.rs` — every SQL statement in the project — is `pub(super)`. That is what "the storage seam is internal" means; do not add a `Repository` port, and do not add a `SearchService` (search is `catalog_search`).

- `catalog_*` covers teams, domains, questions, operators and assets. **Recipes are not reachable through it** — §11.A and §11.B are two verb lists, and `catalog_list`/`catalog_get` refuse `CatalogKind::Recipe` on purpose.
- Archive is `archived_at`. There is no hard-delete path in the crate; `referenced_by` reports what a row is used by.
- `recipe_upsert` is one transaction and advances `rev` once. `recipe_set_membership` / `set_settings` / `set_layout` / `set_overlay` are the same write, named.
- `recipe_set_overlay` carries ScopeConfirm (§2.17): `ThisGame` writes the patch, `Original` writes the catalog row, drops *this* recipe's patch, and leaves every other recipe's patch standing. A per-question duration has no original.
- `build_snapshot` applies overlays to bodies (§4.3) and **refuses a board that names an archived or missing row** rather than quietly dropping a question.
- The Tantivy index is in RAM, rebuilt at open from the catalog, updated by every write, and committed lazily on the next search. Terms match exactly or by prefix.
- Bulk (§2.19) is **one transaction and one fsync per batch**: `catalog_upsert_many` / `catalog_archive_many` / `catalog_restore_many`. The whole batch is validated before anything is written, so a bad row at index 199 leaves the library untouched.
- **A team's `play_count` and `last_play_at` are derived, not stored** (P11.14), and for the same reason as the operator's below: the `teams.play_count` column had a `DEFAULT 0`, was carried through every `team_upsert`, and was written by *nothing*, so the Teams tab reported 0 Plays for a team that had played all season. Both now come from the `plays` projection — a Play's roster is the key set of its `scores_json`, because `record_of` maps over the snapshot's teams and a team that scored nothing is still in there. A Play loaded and never started counts for neither. The columns stay in the schema, dead, beside `operators.plays_run`.
- **An operator's `plays_run` is derived, not stored.** It is `COUNT(*)` over `plays` rows with a `started_at_ms` and that operator's `operator_id`, which the log supplies (`play_load` appends `OperatorSwitched`, `restart` carries it over). The `operators.plays_run` column is still in the schema and nothing reads it — it was a counter no command ever incremented, so every operator had run 0 Plays.
- Tests: `CatalogLocation::Memory` is the adapter, and `tests/catalog_service.rs` runs the same bodies against memory *and* a real file.

## Workspaces (P14, Beta 2.0)

Design: `docs/superpowers/specs/2026-10-21-workspaces-design.md`; plan and test list (with the builder's rulings) in `docs/superpowers/plans/2026-10-21-workspaces*.md`.

- **One file, a `workspace_id` per library row.** Migration 4 adds `workspaces`, `workspace_groups`, `workspace_id` on teams, domains, questions, assets and recipes (`NULL` was the shared library until beta.2's migration 6) and an integer `family_id` for copies. Every existing row moves into one **unnamed** `ws-1`; an empty library gets the same unnamed workspace, so every library has one and Studio asks for its name. Nothing ever suggests a name.
- **The scope lives on the writer connection**: a TEMP table `current_ws` with one row, set at open (`db::bind_workspace`, from the open Play's game, else `workspace.current`, else the first active workspace) and by `workspace_switch`. Every statement in `store.rs` that touches a library row names `IN_VIEW` (this workspace; *current ∪ shared* until beta.2) or `IN_WORKSPACE` (games). Do not pass the workspace as a parameter instead — a forgotten parameter is a leak; a missing TEMP table is a loud SQL error.
- **A save never moves a row.** A new row lands in the current workspace; `ON CONFLICT` never touches `workspace_id` or `family_id`. An id local to another workspace is `NotFound` to a read and `WrongWorkspace` to a write — its id is not free.
- **Reference rules are checked inside the write's transaction**, against the stored rows: a domain holds its own workspace's questions, a game its own workspace's rows, a team or question its own workspace's asset (`ScopeRule`).
- **Plays reach a workspace through their game**; `play_list` and `stats_query` are the current workspace's unless `allWorkspaces`.
- **Each workspace's Demo is its own rows**: `ws-1` keeps the ids the Demo always had (`seed-team-red`), another workspace gets `seed-<ws>-team-red`.
- **Search rebuilds on a switch** (the index holds only rows in view). `SearchIndex::clear` commits before `delete_all_documents`: Tantivy drops committed segments only, so a document still in the buffer survived a clear.
- **The pre-workspaces backup is pinned**: when step 4 is pending the copy is `questiongame-pre-workspaces-<stamp>.sqlite3`, and `backup::prune` skips that prefix.
- **Game defaults and the timer are per workspace** (`WorkspaceDefaults` in `workspaces.settings_json`); the rest of the settings document stays global. A workspace with none yet takes what the app had (the settings document at the first boot, the previous workspace after a switch).
- **Delete permanently** takes only an archived workspace, after a backup, in one transaction; it removes rows, games, Plays and their logs, never an asset file. The current workspace cannot be archived.
- **Transfers carry a closure** (`catalog/transfer.rs`): a domain brings its questions, a game its roster, domains and questions, a team or question its asset. *Copy* makes the picked rows new and **reuses** an active family member in the target for a row that only came along — unless a copied board would then point at a question the reused domain lacks. *Move* refuses (`StillUsed`, naming each user, archived games included) while anything staying uses a row. Each is one transaction, and `transfer_preview` is the same code rolled back, so the confirm cannot disagree with the write.
- **Review fixes (P14):** *Wipe Plays* is this workspace's (`closed_plays` scoped); a picked shared row a move or a share leaves alone comes back in `unchanged`; a reused domain no longer strands the questions that came only with it; the first workspace takes workspace-scoped Demo ids once its own moved away; a boot that fails after the pinned copy takes ordinary rotated copies afterwards (`backup::has_pinned`). Propagation reads where the source asset lives unscoped (`store::home_of`), never carries a local asset onto a shared copy, and checks each board in its own workspace.
- **Families and propagation** (`catalog/family.rs`): a copy and its original share an integer `family_id` (copies of copies too). *Also update {n} copies* carries the **body** — never membership, archive state or overlays; a local asset is carried as its copy in the target workspace, or left alone. A question whose new version would break a board where a copy lives (a difficulty clash, §2.31; an incomplete question, §2.32) is **skipped and named**, through the same `board_problem` check `recipe_upsert` runs. Option ids are kept: they are unique per question. *Save here only* is plain `catalog_upsert`; *Stop following its copies* clears `family_id`.
- Tests: `tests/transfer.rs`, `tests/family.rs`, `tests/workspaces.rs` (scope, rules, verbs, a property test over generated workspaces) and the migration tests in `tests/upgrade.rs` (`db::write_older_schema` builds a real 1.0.2 file from a head library).

## The shared library removed (beta.2)

Design: `docs/superpowers/specs/2026-10-21-remove-shared-library-design.md`; plan and Sonnet's test list (with the rulings R1–R20) in `docs/superpowers/plans/2026-10-21-remove-shared-library*.md`. Why: two audits found about half of ~110 parity gaps came from shared rows (an archive or a re-grade in one workspace breaking another's game, imports refused on a shared domain, twin names, two spellings of a tag, groups reaching every workspace), and the maintainer's own test showed two "Biblie" side by side. Copy and its families keep the useful half — an edit offers to follow its copies — made explicit per edit.

- **Migration 6 is the first Rust step** (`db::apply_step`, `catalog/unshare.rs`), inside the one migration transaction, after the backup, never touching `plays` or `events`. A shared row keeps its id in the oldest active workspace that holds no member of its family (R1); every other workspace, archived ones too, gets it once — a member of its family it already holds when that cannot change what it sees or plays (same archive state, no container would fold two entries into one, a question of the same difficulty and correct marks, a domain no game there boards: R2–R4), else a copy in the family (a Demo row takes that workspace's seed id, one free generation per workspace for the whole Demo: R5). A member stands in for **one** shared row only (`taken`): two shared rows of one family once folded into one row there, breaking a roster's key or dropping a domain member (review). A reused domain gets the shared domain's members it lacked appended, at the end in no group, so a question added to the shared Biblie after B's copy was made stays in Biblie in B. Option ids written after their question's follow a copy's new id, so a Demo copy reads unedited. Each workspace's references are then pointed at its own rows: domain members, rosters, boards, overlay keys and the asset ids inside `patch_json`, team logos, question media. Copied domains take their groups; tags are re-spelled per workspace. Triggers (`unshare::TRIGGERS`) refuse a library row without a workspace from then on — a `NOT NULL` table rebuild was not worth its foreign-key risk.
- **One scope**: `IN_VIEW` is this workspace (the name kept; `IN_WORKSPACE` is the same string), new rows land in it. `Stamps.shared`, make shared / make local, the shared-domain rule, `users_elsewhere`, `BulkReport.shared`, `TagCount.shared` and `TransferReport.unchanged` are gone; `FamilyCopy.workspace` is required. An old payload with `shared: true` still deserializes and lands here.
- **Copy brings a picked question's domains** (`CopyOptions { with_domains }`, default on): it joins the target's copy of each (same family, at the end, in no group — `TransferReport.joined`), else a copy holding only the picked questions and the groups they use; an archived source domain is ignored. Overlay logos come with a copied or duplicated game and are remapped (R13).
- **The Demo in every workspace**: a duplicated workspace's Demo rows take its seed ids, so it is recognised; a workspace whose seed ids live elsewhere takes the next generation (`seed-<ws>-r2-…`) — the moved-Demo collision of review P4, for every workspace, not just `ws-1`.
- **`workspace_switch` rebuilds the index before it writes `workspace.current`**, and re-binds the old workspace if it cannot: host and Studio never disagree about where they are.
- **`is_empty_everywhere`** (unscoped) is what the Beta welcome checks before a stable library replaces the file: an empty workspace is not an empty library.
- Not added: an unscoped asset read for Plays (R11) — nothing reads a snapshot's asset ids by id yet.

## Copy, import and refusals (beta.3)

Design: `docs/superpowers/specs/2026-10-21-beta3-copy-import-editor-design.md` (rules 1–11).

- **A copy keeps archive state**: `transfer.rs` writes every row active, then archives each created row whose source was archived (`store::set_archived`, a last pass) — an archived question copied with its domain arrives archived, as Duplicate already did.
- **A copied game loads as its original does**: a board question that only came along is reused only if the target's family member has the same difficulty and the same completeness (`complete::effective_gaps` empty or not); otherwise it is copied fresh. Before this, a re-graded copy in the target broke the copied board's walk (§2.31) and the game refused to Load.
- **Twins are said, not refused**: `TransferReport.twins` lists each picked team, domain or game that arrives beside an active row of the same name (folded) in the target — "team Red". No uniqueness rule anywhere.
- **Refusals name rows**: `store::row_name` (a name, a stem cut to 40, an asset's path, an operator's display name) is what `StillUsed`, `ScopeRule` and `WrongWorkspace` say; `referenced_by` returns a sentence — "the game Friday", "the games A and B", "the game X and 3 more", "an open Play" — never an id or a kind word ("a a recipe board" is gone).
- **Import resolves names in this workspace, oldest first**: of two domains with one name the oldest-created takes it; a code names exactly one. Each `ImportRow` carries `landing` ("History (HIS_100)", "Rome (new)", "History (HIS_200), one of 2 named History"), its cleaned `tags`, and for a duplicate `duplicate_of` — the library question's stem, or "row 4" of the same file. `fake/import.ts` mirrors all three.

## Domain groups, tags, bulk edits (P15)

Design: `docs/superpowers/specs/2026-10-21-groups-tags-bulk-design.md`; plan and Sonnet's test list (with rulings) in `docs/superpowers/plans/2026-10-21-groups-tags-bulk*.md`.

- **Migration 5**: `domain_groups` (with their domain, `ON DELETE CASCADE`; no workspace column — a group lives where its domain lives), `domain_questions.group_id` (`ON DELETE SET NULL`), `question_tags(tag, tag_key)` with `tag_key` the Rust `to_lowercase` fold — never SQLite `NOCASE`, which folds ASCII only.
- **A member's group rides on `DomainMember`**: `domain_upsert` writes exactly the groups it is sent and refuses a group of another domain, so every caller that rebuilds members carries `group_id`. `Domain.groups` is read-only on a save; the group verbs write it.
- **Tags ride on `Question`** and are cleaned in the one write every question takes (`question_upsert` → `groups::clean_tags`): trimmed, 1–40 characters, one per fold, the spelling on the earliest-created question in view kept, at most 20 (refused, never trimmed). So import, transfers, propagation and bulk edits all hit the same rules. Tags are body — copies and *Also update copies* carry them; a group is membership — never carried, and a reused domain keeps its own (`write_copy_with_groups` gives a copied domain its own groups).
- **Bulk edits** (`catalog/bulk.rs`): one transaction, refused whole, `changed / unchanged` counts, a preview that is the write rolled back, copies untouched; the search index rebuilds after. *Set difficulty* adds no refusal: a board left with a clash is Load's to report, as for one edit.
- **Groups are not part of the Demo** (review): `seed::same_body` levels a domain's groups and members' `group_id` before comparing, and *Restore sample game* (Overwrite) carries the stored members' groups across — so grouping a demo question is not an edit, and restoring does not strand a group.
- **`domain_upsert` checks every member's group before writing**: another domain's is "that group belongs to another domain", a deleted one "that group no longer exists" — never a raw foreign-key failure.
- **Membership edits move the changed questions' `updated_at`; every group verb moves its domain's. `domain_group_rename` / `delete` return the group's stored domain, which the app announces.
- **A moved question re-spells its tags** to the target workspace's spelling (`store::tags_respell`, with the target bound); a rename in one workspace leaves other workspaces' local questions alone, and the dialog says so.
- **Lists read tags and groups in one query each** (`all_question_tags`, `all_domain_groups`), and the search index reads a question's tags as stored, not as sent.
- **Manage tags** renames and deletes over questions in view in SQL (`store::tag_rename`, `tag_delete`); a merge never adds a tag, so it cannot pass the cap. A rename counts and touches only rows whose spelling changes.
- `db::write_older_schema` replaces the rows an older step seeds and copies with foreign keys off, so a v4 library can be written for the migration tests.

## One arithmetic, and rules the operator can see (P11.12)

The design is `docs/v1/05_STUDIO_DESIGN.md` §14. What a later phase must not undo:

- **The award formula exists once, in `crates/host/src/explain.rs`.** `award::award_points` is `explain(..).points`; `base_points` and `speed_multiplier` are fields of the same `AwardBreakdown`. A second copy is how the ledger and the scoreboard drift, and the Statistics ledger only means anything because it reads the steps the Play was actually paid from. `AwardBreakdown` records *which band paid* (`BaseSource::Band` carries the index and the resolved `from..=up_to`) and *why* a speed factor did nothing (`ModeOff · OperatorPace · NeverLocked · WeightZero · OutsideWindow`) — five distinct ways a weight the operator set does nothing, each worth saying out loud.
- **The award is a pure function of `(difficulty, verdict, lock progress, streak)` and the frozen settings.** It never reads the domain, the team, the round or the position on the board — so difficulty 21 pays the same everywhere. `crates/host/tests/award_compound.rs` is the proptest suite over the real compound space (mode × lock-speed base × option × weight × window × steps × linear|bands × partial × order × cap × bonus × cascade); writing it found two real defects on the first run — a partial share could exceed the whole award, and two bands sharing a ceiling produced an overlapping span.
- **`speed_window` and `speed_steps` default to the pre-P11.12 formula and must keep doing so.** `Fraction(1.0)` with no steps is `remaining / duration` byte for byte; both carry `#[serde(default)]`, so an old `PlaySnapshot` deserialises into the rules it was played under. `Ms(n)` is the one that makes the same answer *time* worth the same on every question, which is the answer to a board with per-question duration overrides. `speed_steps` bands the bonus so two answers the operator cannot tell apart cannot score differently.
- **`DifficultyMap::spans()` is the one place bands are ordered and their lower bounds derived**, so the award, the ledger and the preview cannot disagree about which band a difficulty falls in. A band an earlier one already covers is marked `reachable: false` and **kept**, not dropped — an operator who typed it needs to be told why it is dead, and a ladder drawing it as a range would be drawing an overlap.
- **Uneven domains are not an award problem.** The award never reads domain membership, so a three-question domain and a thirty-question one pay the same for difficulty 21. What they change is the ceiling and the walk, and that is reported by `BoardShape` in the **Board** section, not fixed by a rule in Rules. The readout adapts to the shape: `Aligned` (same count *and* same ladder) collapses to one rung table because then one table is the whole truth; `Uniform` and `Ragged` show the ladders side by side.
- **`RuleState` is three-valued, and `Off` is not `Disabled`.** `preview::rules_for` is the single place that answers both "can this key do anything right now" (the §4.2 interlock) and "what is it set to" (the settings document), for every `AWARD_KEYS` key. Answering only the first is a bug that ships: a switch that is *usable but off* has no interlock entry, so Rules rendered it as **In use** and claimed partial credit was on while the form right above it showed the switch off (reported 2026-09-10). An interlock outranks an off value — "lock-speed scoring is off" is more useful than "the weight is 0" — and `Active` always carries what the key is set to, because "In use" alone never answers the question the operator is asking. **Never infer a setting's value from the absence of a disabled entry.**
- **`crates/host/src/preview.rs` is pure** — no catalog, no Play, no clock — and every number in it comes from `explain`. A preview that computed its own numbers would be a second rules engine, and the first thing it would do is disagree. `CatalogService::preview_board` is `build_snapshot`'s lenient cousin: same overlays, but it *skips* a row it cannot read instead of refusing the board, because a preview of an unfinished board is the normal case.
- **`rules_preview` is composed in the app crate**, the way `play_load` already is: the catalog knows the board, `FlagService::interlocks_for` knows the §4.2 table, `preview::build` knows the arithmetic. `interlocks_for` exists because `disabled()` can only answer for the recipe **in Control** — `RulesSection` used to re-derive "the weight is inert" and "the timer is off" client-side, a second copy of an interlock. Do not put those back.
- **`stats_query` gained `detail: u32`, not a second verb.** §13.1 is one command and one document; the ledger is a *detail level* of the same question. `0` is the default, so a view that draws only numbers pays nothing for one it does not. `stats::awards` is the fold, `stats::facts` maps it.
- **In the ledger, `points + bonus` is the truth and `award.total` is the working.** They agree — `demo_scenarios.rs` s16 replays a whole Demo asserting it — but a log written by an older build is still a record of what that Play paid, so the TOTAL column reads the record and the breakdown explains it. A recomputation must never rewrite a score. There is deliberately **no** assertion inside the fold: a hand-written or older log is exactly what the ledger has to survive.
- **`Panel` takes named props only**, so a `data-` hook on it is silently dropped and a test keying on one asserts nothing. **`Text` is inline by default** — a label and the sentence under it need `as="div"`. **`NumberField` renders a text input**, so its role is `textbox`, not `spinbutton`.
- **The P11.7 clock guard now exempts files that never touch the play-state store.** The ledger names `remainingMsAtLock` throughout, but that is the clock as it stood when a turn *resolved*, out of `stats_query`. The rule is about subscribing to a live Play for a number that moves at 10 Hz; pointing it at the word instead of the thing would have forced an allow-list that grows forever.

## One question per difficulty, per domain (P11.13)

`optimized_first_spec.md` §2.31. The **library** is unconstrained — a domain may hold as many difficulty-10 history questions as the author writes, and `catalog_*` refuses none of them. A **recipe board** selects one of them. Teams choose a domain, never a question, and `explain` never reads *which* question it was, so two questions at one difficulty pay the same, are indistinguishable to the team choosing, and put a step of zero in `BoardShape`'s ladder.

- **`crates/host/src/board.rs` is the whole rule and it is pure** — no catalog, no clock, no recipe. Every enforcement point adapts its own data into `(id, effective difficulty)` pairs and calls `clashes`; a second spelling is how the write and the Play start disagreeing. The difficulty compared is always the **effective** one (`overlay ?? catalog`), because that is the one the award and the queue read.
- **Two doors, not one.** `recipe_upsert` is the funnel for the checkbox *and* every other recipe write, but **`recipe_set_overlay` does not go through it** — it writes overlays directly and bumps `rev` itself. So `CatalogService::check_board_difficulties` has two call sites, and the overlay one checks the recipe the write *would produce*, before writing: a `ThisGame` patch, a **reset** (which hands a question back its catalog difficulty), and `Original` (whose new catalog value arrives as the `pending` parameter, so the row is not written and then found illegal).
- **A board can become illegal from outside**, and that is deliberate. Re-grading a question in the Questions tab can collide a board that was legal when saved; the library does not veto an edit on a recipe's behalf, which is what `referenced_by` exists for. So `build_snapshot` re-checks — the same second line `play_load` keeps for a snapshot's settings — and `PreviewWarning::DuplicateDifficulty` says it in Game ▸ Rules before Load does.
- **Studio dims, it does not decide.** `apps/studio/src/host/board.ts` (`blockedMembers` · `oneQuestionPerDifficulty`) spells the rule for the Board section the way `host/session.ts` does for the Action Panel. It is derived from `recipe.board` and the difficulties the rows already render — **not** from `rules_preview`, which is a Query keyed on `rev` and lags a checkbox by a refetch; the dim has to be instant to read as dynamic. A blocked member is disabled with the reason at 40% (§4.2), and a **selected** member is never disabled, or a legacy board would take away the checkbox needed to fix it. Add domain ticks one per difficulty, `difficulty ASC, id ASC`.
- **The fake refuses too**, `Original` included. A shell that only stays legal because the fake never refuses is the shell the app rejects.
- **A game may allow repeats** (P12.7, `board.allow_repeated_difficulty`, off by default). Every door calls `board::check(allow, pairs)`, which is `None` when allowed — the one place the switch is read — and every door reads it from the **recipe** (`recipe.settings.board`, `game.board` in the preview), never a live copy. It is in `GAME_AFFECTING_KEYS`, so it freezes at Play start; it is *not* in `FrozenSettings` because the snapshot already is the board it allowed, and the Rules table skips `board.*` because it moves no award. `recipe_set_settings` funnels through `recipe_upsert`, so switching it off on a repeating board is refused naming the clash — in the fake too. `demo_scenarios.rs` s17 plays two tens in a row.

## Incomplete questions, import, and a second Demo (P11.17)

`optimized_first_spec.md` §2.32 is the rule; `05_STUDIO_DESIGN.md` §17 is the design, and its §17.2 is the import file format.

- **Floor vs gaps.** `Question::validate` refuses only the floor — neither stem nor option, an option without text, two option ids alike, a difficulty outside 1–100. The five **gaps** (stem · options · correct · difficulty · active domain) are spelled once, in `crates/host/src/catalog/complete.rs`; `apps/studio/src/host/question.ts` spells them for display (the mark, the filter, the editor's live list) and decides nothing.
- **`Question.difficulty` is `Option<u8>`**, `number | null` on the wire, stored as `0` in the `NOT NULL` column — `store.rs` is the only place that knows.
- **A board is judged on the effective body** (overlay applied), at the same two doors as §2.31 — `check_board` is called by `recipe_upsert` and by `recipe_set_overlay`, which checks an `Original` edit on the row it *would* write — plus `build_snapshot` as the second line. A this-game difficulty can complete a question for one show.
- **Import is a pure planner run twice.** `catalog/import.rs::plan` answers the preview and then the write (`catalog_upsert_many`, one transaction), so the report and the rows cannot disagree. A commit announces one `catalog-changed` per kind, never one per row. `apps/studio/src/host/fake/import.ts` mirrors the planner case for case — change both together, and `suggest_code` with `host/domain.ts`'s `suggestDomainCode`.
- **Two Demos share no row.** `seed.rs` builds both from one `Document` table; the English ids and bodies are byte-identical to before, so an old install's edited-row count is unchanged. `catalog_seed_demo` / `catalog_seed_status` take `demo: 'en' | 'ro'`, defaulting to `en`. Romanian copy is comma-below `ș ț` — `seed.rs` has a test for it.
- **The editor saves an incomplete question** and drops blank option rows on save; a gap never disables Save.

## How the host stack arrived (P5–P6)

**Installed (P6):** `serde`, `serde_json`, `thiserror`, `uuid`, `rusqlite` (`bundled`), `tantivy`, `tracing`, `proptest` in `crates/host`; `tauri`, `tauri-build`, `tokio`, `tracing-subscriber` in `crates/app` — edition 2024, workspace deps in the root `Cargo.toml`. **`tokio` waited for P6 on purpose**: nothing in the host is asynchronous (`rusqlite` and Tantivy's writer are both sync, and avoiding async catalog calls was half the reason for choosing `rusqlite`), so until something awaited, a runtime was weight rather than readiness. What awaits is Tauri's async commands and the 100ms tick.
