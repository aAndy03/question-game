# Tests and tooling as built

The end-to-end suite and the codebase map. The rules here are binding; `CLAUDE.md` points here instead of carrying them.

## The end-to-end suite (P12.14)

`e2e/` drives the **real app** through WebDriver: WebdriverIO, `tauri-driver` and the WebView2 driver (`cargo install tauri-driver --locked`; `msedgedriver-tool` fetches the driver matching the installed WebView2). **Windows only** — macOS's WKWebView has no WebDriver. It is **not** run on CI (since v1.1.0): the runner's ~1024-wide screen and older WebView2 failed the release runs on layout alone. `npm run e2e` runs on the maintainer's Windows machine before every tag.

- **It drives a third identity, `org.questiongame.e2e`** (`tauri.e2e.conf.json`, `npm run e2e:build` = `tauri build --debug --no-bundle` with that overlay), so its library, log and WebView2 profile are folders no show lives in. `identity::check` admits it only in a built app, never a dev server. **`e2e/support/folders.ts` is the only code that deletes anything**, and it refuses any folder not named `org.questiongame.e2e` — keep it that way; never point the suite at `org.questiongame.desktop` or `org.questiongame.app`.
- **Every spec starts from a reset folder** and, if `SEEDS` names one, a library written by `cargo run -p questiongame-host --example e2e_library` — the Demo, an active operator, **unstamped as 1.0.1 left it** (so the app backs it up and opens *What's new*; `closeWhatsNew()` for specs about something else), and `--broken-board` for a board re-graded from the library. **The library is written at schema 3** (Beta 2.0): built at the head schema beside the path, then copied with the columns 1.x had (`db::write_older_schema`), so the app migrates it into one unnamed workspace and asks its name — `nameWorkspace()` answers, and checks the field starts empty with no placeholder; `closeWhatsNew()` calls it first. An empty library (first run, Beta *Start empty*) asks *Create your first workspace* the same way. `workspaces.e2e.ts` names, creates, copies, shares and propagates on the real app.
- Specs: `first-run` (operator, Demo, shell), `show` (Load opens Stage on Idle, Start Play, a domain, *Question* on air — Stage changes screen only when the operator picks one), `load-refusal` (P12.8 from the Roster), `upgrade` (P12.6 backup + P12.10 *What's new*). A new spec must be added to `SEEDS`, or the run refuses it.
- **Read the page the way a person does**: `press(name)` prefers a `<button>` with that text over any other element of the same accessible name (the sidebar's *Show* heading vs the collector's *Show*); Stage's screen is its `data-screen`. A failed step leaves a screenshot and the page source in `e2e/.artifacts/`.
- **Four things that broke the suite once.** The e2e build never opens the debug port 9222 that debug builds open for `npm run js-stack` (`windows::debuggable` reads the identity) — msedgedriver launches WebView2 on a port of its own. The build `onPrepare` starts runs **without `NODE_ENV`**: WebdriverIO sets it, a Vite build that inherits it compiles the dev-only code in, and the release check refuses the build. When it ran on CI it needed **`windows-2022`**: on the windows-2025 image (`windows-latest`) WebView2 ignores the debugging port msedgedriver passes, so no session starts though the app boots fine ([actions/runner-images#14738](https://github.com/actions/runner-images/issues/14738)); if 2022 is retired, attach instead — the app opens its own port and msedgedriver connects via `debuggerAddress`. And a session that never starts leaves no screenshot: the e2e app's `questiongame.log` (in `%APPDATA%\org.questiongame.e2e`) says whether it booted, refused or panicked.
- **The Beta specs** (P13.1) run the same e2e binary as questiongame Beta: `CHANNELS` beside `SEEDS` names each `beta-*` spec and what its "stable library" is — the Demo, nothing, the Demo with a running stable app (`crates/app/examples/hold_lock.rs` holds the lock until the spec drops a `release` file), or bytes that are not a library. That library lives in `<tmp>/questiongame-e2e-stable`, which `folders.ts` alone creates and deletes, refusing any other path. `launchEnv` sets both variables for a Beta spec and **removes** them for every other, so a value left in the shell cannot turn a stable spec into a Beta one. `onPrepare` / `onComplete` read the names in the installed and dev folders (never write) and fail the run if they changed.
- Not here: several displays, the Atomos, the installer itself (it would overwrite the machine's installed app). Those stay manual.

## The codebase map (P12.13, P12.15)

`codemap.yaml` at the root is **generated** — `npm run map` — and never edited by hand. It lists the surfaces that break across versions: every IPC command (params, return, which webviews may call it, and which Studio files call it), every event and its payload, the contract exports and `CONTRACT_VERSION` on both sides, every settings key with `GAME_AFFECTING_KEYS`, the migrations and meta keys, the host crate's public API and the app crate's modules — and since P12.15 the rest of the tree: **`stage`** (the commands Stage calls, the events it hears, its query flags, the `StageCopy` keys and languages), **`packages`** (`text`'s API, both design systems' files and CSS custom properties, each package's `exports`), **`windows_and_permissions`** (each capability's windows and permissions, every label `windows.rs` creates), **`config`** (`tauri.conf.json` and its dev, e2e and macOS overlays, the identity consts), **`build`** (npm scripts, workspaces, Cargo members and dependency specs, CI jobs), **`e2e`** (spec titles, `SEEDS`) and **`fixtures`**. File paths, no line numbers, sorted, so **`git diff v1.0.2 -- codemap.yaml` is what changed in a release**; consts carry a short hash so a changed value shows even when its name does not.

- **`npm run map:check` fails when the committed copy is stale**, in CI and in `npm run release`: a change to any of those surfaces is not done until the map is regenerated and the diff read.
- **`mismatches:` must stay empty.** It cross-checks the Rust commands against the contract's lists and `generate_handler!`, the events, and the two `CONTRACT_VERSION`s, and since P12.15 also: Stage's calls against `STAGE_COMMANDS`, Stage's events against `STAGE_EVENTS`, `TEXT_KEYS` against the copy tables, the copy languages against `STAGE_LANGUAGES`, every window label against a capability, every config overlay's identifier against `identity.rs`, every spec against `SEEDS`, and every fixture against `fixtures/index.json` — each check has a unit test that makes it fire; its first run found the contract's `STAGE_COMMANDS` missing `client_log` and `perf_report`, which `guard.rs` allowed.
- Rust is read by `tools/codemap` (a dev-only `syn` crate, outside the licence audit's graph — `test:tools`, `lint:tools`); TypeScript by `scripts/lib/codemap.ts` and `codemap-surfaces.ts` (the `typescript` compiler API, a hand-rolled YAML emitter, no YAML dependency). A Studio call whose command is not a string literal is listed under `dynamic_call_files` rather than guessed. Detection is literal: Stage's `client_log` goes through a variable and is not listed; a multi-line `run:` in a workflow is skipped; the `mirror_label()` window is tested as `stage-2` and `stage-3`.
