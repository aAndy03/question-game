# Stable 1.1: finding things in the library — design

*2026-10-20. Status: approved 2026-10-20. Release B of four (A channels ✓ → **B stable 1.1** → C Beta 2.0 workspaces → D groups, bulk, tags). Built on `release/1.x`, merged forward into `main`.*

The maintainer asked for: shared and per-tab filters, sort, a list view broken up by headers (by domain, difficulty, …), and pagination at 100 per page by default that works together with filters, sort and headers. They asked for the design to be proposed rather than discussed, so **every decision below not in that sentence is the designer's call**, marked *(call)*.

## Intent

A library grows. A season of shows is hundreds of questions across a dozen domains, and today the only way to find one is to scroll or type in Search: there is no way to say *"the hard History questions I haven't finished"*, to change the order of a list, or to see a list broken up by what it is about. 1.1 makes every library tab answer *"show me only these, in this order, grouped like this"* — and does it the same way on every tab, so learning it once is enough.

Success: on the Questions tab, an operator narrows 3,000 questions to "History, hard, incomplete", sorted by difficulty, grouped by domain, a page at a time, in a few clicks — and the same controls in the same places work on Teams, Games and Operators. Nothing about a show, a Play or the library's data changes.

## Goals

1. **Filters** on every library tab: a few **shared** ones that mean the same everywhere, and **local** ones that belong to one tab.
2. **Sort** on every tab: pick a field and a direction; in table view, column headers sort too.
3. **Headers** (*Group by*): break a list into sections under a header with a count, by a field that tab offers.
4. **Pages**: 100 rows a page by default; filters, sort and headers all work across pages.
5. **One implementation, used by every tab** — a list-view model the tabs declare, not four hand-built toolbars. This is also what release D's bulk actions will build on.
6. A *What's new* entry for 1.1.0 (EN, RO).

## Non-goals

- Saved filter presets / named views (still out of v1, `05_STUDIO_DESIGN.md` §13.6).
- Tags on questions, groups inside domains, new bulk actions — release D.
- Workspaces — release C.
- Any change to the host's data, schema, commands or events. *(call: everything here is a view over what `catalog_list` already returns; see Constraints.)*
- Filters, sort or pages on Statistics, Control, Screens or Settings.

## Anti-goals

- A query builder. No AND/OR trees, no free-text field conditions. Each filter is one obvious control.
- A filter that hides rows the operator then acts on without knowing: **a bulk action never reaches a row that is filtered out or on another page without saying so.**
- Four tabs that each work a little differently.
- Losing the operator's place: editing or archiving a row must not throw them back to page 1 or reset their filters.
- Anything slower than today on the 3,000-question library the perf log was measured with.

## Constraints (from the repo)

- `catalog_list { kind, scope }` returns **every row at once**; there is no paging anywhere, and search is Tantivy hits intersected with that full list client-side (`host/queries.ts`, `useSearch`). Questions belong to domains through `Domain.questions` (a question can be in several). A question has no tags; recipes have `folder` and `tags`.
- `LibraryList` (TanStack Table v8) sorts from props only, has no filter or pagination model, and virtualizes tables over 200 rows. Its `data` must be referentially stable (`NO_ROWS`, P11.3) — the same rule binds every array a new model hands to TanStack.
- Toolbar order is fixed by `05_STUDIO_DESIGN.md` §4.6: *Search · filter · sort · view switch · archive toggle · New*. Chips have a closed vocabulary (§4.6); a new chip is added there first.
- Chrome store (zustand, persisted per operator) holds view preferences only; a test bans Play-shaped keys (`score`, `ring`, `session`, `timer`, `team`) — new keys must not trip it.
- HeroUI v3 as shipped; `heroui-react` skill before markup. Studio is English except *What's new* and Beta's welcome.
- Stable-safe: nothing here may depend on the Beta-only code on `main`.

## 1. Where the work happens *(call)*

**In Studio, over the full list the host already sends.** Filtering, sorting, grouping and paging are a pure function of `(rows, view state)` in the webview. The library is a few thousand rows at most, already fully loaded today for search, and the P11 perf log puts a 3,000-row list well inside a frame. No IPC, no schema, no migration — which is what makes this safe for stable and trivially mergeable into `main`.

The host stays the source of **truth** (rows, archive scope, search hits); Studio only decides **what is shown**. If a library ever outgrows this (tens of thousands), paging moves to the host behind the same view model — not in 1.1.

## 2. The view model *(call)*

One module, `host/listView.ts` (pure) + `useListView` (hook), used by all four tabs:

```
ListSpec<Row>          declared once per tab
  filters:  FilterDef[]   — id, label, kind (choice | multi | range | toggle), how to read a row
  sorts:    SortDef[]     — id, label, how to compare, default direction
  groups:   GroupDef[]    — id, label, the header(s) a row falls under, header order
  defaults: { sort, group, pageSize }

ListViewState          per tab
  filters (values) · search text · sort {id, dir} · group id | none · page · pageSize

listView(rows, spec, state) → { pageRows, groups on this page, total, matching, pageCount, active filter chips }
```

The model is pure and tested on its own; `LibraryList` renders its output. TanStack Table stays the table engine for selection and columns; filtering, grouping and paging are done by the model *before* the rows reach it, so `data` is one memoized array.

## 3. Filters

**Shared** (same control, same meaning, every tab):
- **Search** — as today (Tantivy hits ∩ rows), **without today's cap** of 200 hits (500 for questions): the limit becomes the size of the list, so a paged, filtered result never silently loses matches. *(call)*
- **Status** — the existing *Active / Archived* toggle, plus **All** *(call)*.
- **Changed** — *any time · today · last 7 days · last 30 days*, on `updatedAt` *(call)*.

**Local** (one tab):

| Tab | Filters *(call)* |
|---|---|
| Questions | Difficulty band (easy · medium · hard, multi) · Difficulty range (1–100) · Answer type (single · multiple) · Completeness (all · incomplete · complete — replaces today's *All · Incomplete* tabs) · Domain (multi; only under *All questions* — picking a domain in the pane already scopes it) · Origin (sample · mine) |
| Teams | Played (any · never · at least once) |
| Games | Folder (multi) · Tag (multi) · Playing now |
| Operators | Has a PIN · Active operator |

- One **Filters** button in the toolbar opens a popover with the tab's local filters; the button shows how many are on. **Active filters show as removable chips** in a row under the toolbar, with **Clear all**. *(call)*
- Values combine with AND across filters, OR within a multi-select. That is the whole grammar.
- The empty state `noResults` gains **Clear filters** next to *Clear search*.

## 4. Sort

- A **Sort** menu: field + ascending/descending. Fields per tab *(call)*: Questions — difficulty · text · domains · changed · created; Teams — name · plays · last played · changed · created; Games — name · teams · questions · changed · created; Operators — name · plays run · last active · created.
- **While Search has text, a *Best match* sort appears and is chosen** (Tantivy's score, today thrown away); clearing search returns to the previous sort. *(call)*
- **Table view gains a header row** with the sortable columns; clicking one sorts, clicking again flips direction. Grid view uses the menu only. *(call)*
- Ties break by name/text, then id, so the order is stable across renders and pages.

## 5. Headers (Group by)

- A **Group** menu beside Sort: *None* plus the tab's groupings *(call)*: Questions — domain · difficulty band · answer type · completeness; Teams — played / never played; Games — folder · status (playing · ready · archived); Operators — none offered.
- Each header shows its label and **its count across all pages** ("History · 48").
- Headers can be **collapsed**, per group, for the session (not remembered). A collapsed group shows its header only, its rows **take no page slots**, and *select all* leaves them out — the bulk bar says so. *(call)*
- Groups are ordered by the grouping's own order (difficulty bands easy→hard; domains by name; *No domain* / *No folder* last); rows inside a group follow the sort.
- **A question in several domains appears under each of its domains**, marked *also in …* (this only happens grouped by domain under *All questions*). Each appearance is a **row**, keyed `<group>:<id>`; pages are cut by rows. The footer counts rows, and adds the question count when the two differ: *"101–200 of 1,310 rows · 1,234 questions"*. Selection and bulk work on **questions**: selecting one appearance selects them all, and a bulk action touches each question once. *(call)*

## 6. Pages

- **100 rows a page by default**; page size *50 · 100 · 250 · All*. *All* keeps today's behaviour, virtualized over 200 rows in table view.
- Paging is over the rows on screen — after filtering, sorting and grouping, leaving out collapsed groups: a group can continue onto the next page, and its header repeats there as *"History · 48 (continued)"*.
- A footer: **"101–200 of 1,234 questions"** with previous / next, and page numbers when there are more than three pages.
- **The page resets to 1** when search, a filter, the sort, the group or the page size changes; it **does not** when a row is edited, archived or restored (if the page empties, it moves back one).
- Opening a row and coming back returns to the same page with the same row in view.

## 7. What is remembered *(call)*

- **Per operator, per tab, persisted**: sort, group, page size — preferences, like grid/table today.
- **For the session, per tab**: filter values, search text, the page, collapsed groups — like the Active/Archived toggle today. A fresh start shows the whole library, so nobody wonders where their questions went.

## 8. Selection and bulk (what exists today)

- Today's bulk archive/restore (Teams, Questions) keeps working, scoped by the model: **select all selects the matching rows across every page**, and the bar says so: *"48 selected (12 on this page)"*.
- **Changing a filter or search clears the selection** — a row that has left the view is never acted on.
- **Status *All*** mixes active and archived rows; the bulk bar then offers both, each with the count it applies to — *Archive 30 · Restore 18* — and each touches only the rows it fits. *(call)*
- New bulk actions are release D.

## 9. Layout and vocabulary

- Toolbar, every tab, in §4.6's order extended *(call)*: **Search · Filters · Sort · Group · View · Status · New**; the active-filter chip row under it; the page footer under the list.
- The Questions tab's *All · Incomplete* tabs become the Completeness filter, with the incomplete count kept on the Filters button's hint.
- `05_STUDIO_DESIGN.md`: §4.6 toolbar order, a new §20 for the list view (controls, chip row, group header, page footer, empty states), and the new copy in `copy/`. The unused `LIST.sort*` strings already in `copy/index.ts` are used rather than duplicated.

## 10. Release

- Built as phases on `release/1.x` (`P13.2…`) — the pure model and the Questions tab first, then the other three tabs — each merged forward into `main` with no conflicts expected (Beta's changes on `main` touch none of these files except `App.tsx` and `SidebarNav.tsx`, which this does not change).
- `What's new` 1.1.0 in English and Romanian, plain words.
- `npm run version:stable -- minor` → 1.1.0 when the maintainer says; publishing is their tag.
- Tests: Sonnet proposes the list (as for release A); the floor is the pure model (every filter, sort, group, page edge), each tab's spec, the toolbar order, persistence per operator, selection rules, the NO_ROWS stability rule for every array, a 3,000-question performance check, and one e2e spec on the Questions tab.
