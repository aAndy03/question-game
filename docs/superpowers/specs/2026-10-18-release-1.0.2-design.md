# Release 1.0.2 — design

*2026-10-18. Status: draft for approval.*

## Intent

A month after 1.0.1, ship a maintenance-and-features release that existing
operators can take **by running the new installer over the old one**, with
their library carried forward and backed up automatically. The app has no
auto-updater; this release adds the smallest honest substitute — it tells the
operator a newer release exists and links to it.

Success: an operator on 1.0.1 downloads `questiongame_1.0.2_x64-setup.exe`,
runs it, opens the app, sees *What's new* once, and finds every team, question,
game and Play exactly as they left them — with a backup of the pre-upgrade
library on disk.

## Goals

1. **Dependencies current.** Every npm and Cargo dependency updated to its
   latest compatible release (HeroUI v3, React, Tauri 2, Vite, TanStack, etc.).
2. **Repeated difficulties on a board (option).** A per-game switch that lets a
   board hold more than one question at one difficulty within one domain.
3. **Refusals surface globally.** A refused command whose notice is addressed
   to a field on another page (the Load refusal naming a Board problem) is also
   visible from wherever the operator is.
4. **Update notice.** On each start, check GitHub for a newer release; Settings
   has *Check for updates* and an off switch. Both open the release page.
5. **What's new.** The first launch after an update shows the changelog for the
   versions the operator has not seen.
6. **Safe upgrade.** The library is backed up before any migration and on every
   version change, automatically, with bounded retention.
7. **Verified.** All suites, the release check, and a real install-over-1.0.1
   upgrade test pass before the tag is pushed.

## Non-goals

- No auto-download or self-install (no `tauri-plugin-updater`, no signing keys).
- No restore-from-backup UI. Backups are files; restoring is manual and documented.
- No change to the library's own rules — the library was already unconstrained.

## Anti-goals

- An upgrade that loses or silently rewrites an operator's data.
- A network failure that shows anything during a show. Offline is normal.
- A new toast family or a second notice system.

## Constraints (from the repo)

- Version lives in three files held by `crates/app/tests/bundle.rs`
  (`Cargo.toml [workspace.package]`, `crates/app/tauri.conf.json`, root
  `package.json`). Release steps memory: bump all three, latest-Rust clippy,
  push `main` before the `v*` tag.
- `release:check` forbids network loads in `dist/` — the update check runs in
  Rust, not the webview.
- `npm run build` audits licences (`scripts/lib/notices.ts`); any new crate
  must pass it. Do not widen `ALLOWED`.
- Docs change in the same commit as the code (`05_STUDIO_DESIGN.md`,
  `optimized_first_spec.md`, `CLAUDE.md`, `04_ROADMAP.md`). Each piece is a
  phase commit on `main` (P12.5 …).
- HeroUI v3 markup is written with the `heroui-react` skill, never from memory.

---

## 1. Dependency updates

- `npm outdated` / `cargo update` + `cargo outdated`; take every
  semver-compatible update. A **major** bump (any package) is taken only if its
  migration is small and the suites pass; otherwise it is left and listed in
  the commit message.
- HeroUI: stay on v3 (`@heroui/react`, `@heroui/styles`), latest 3.x. Re-check
  the two overlay rules and the `Switch.Content` rule in CLAUDE.md still hold.
- Re-run the licence audit; a new transitive licence outside `ALLOWED` is a
  stop-and-ask, not a list edit.
- Rust: latest stable toolchain clippy (`-D warnings`) on both crates.

## 2. Repeated difficulties on a board

**Decided (operator):** a per-game switch, off by default, frozen at Play start;
same-difficulty questions are asked in a fixed order.

- New Game-tab key **`board.allow_repeated_difficulty: bool`**, default
  `false`, **recipe-level only** *(builder's call: no `globals` default, no
  Settings switch, no live copy — the recipe row is the one source every door
  reads, so the write and the Play start cannot disagree)*,
  `#[serde(default)]` so every existing recipe and `PlaySnapshot`
  reads as today's rule. It is **game-affecting** (frozen at `play_start`,
  visible but disabled while a Play is open), because it changes what a Play
  can contain.
- `crates/host/src/board.rs` stays the one place the rule is spelled:
  `clashes` is unchanged; the callers (`recipe_upsert`/`check_board_difficulties`,
  `recipe_set_overlay`, `snapshot::build`, `preview::build`) skip the check when
  the recipe's switch is on. Prefer a single `board::check(allow, pairs)` so the
  switch is read in one place.
- **Order:** the walk is already `difficulty ASC, id ASC` (`SnapshotDomain::new`);
  no change. Two difficulty-10 questions are asked one after another, lower id
  first.
- **Award:** unchanged — two questions at one difficulty pay the same. The Rules
  preview's `BoardShape` ladder must render a zero step without calling it an
  error; `PreviewWarning::DuplicateDifficulty` is not raised while the switch is on.
- **Turning the switch off** on a board that now holds repeats: the write is
  refused like any other illegal board (the operator removes the extras first).
  The refusal names the clashes.
- **Studio:** a switch in Game ▸ Board; when on, `host/board.ts`
  `blockedMembers` dims nothing for difficulty; *add domain* ticks every
  question (still `difficulty ASC, id ASC`). Fake host mirrors it.
- **Spec:** amend `optimized_first_spec.md` §2.31 (and the §2.2 note) — the
  rule becomes the default, the switch is the exception, with the why.
- Tests: `board.rs` units; `catalog_service.rs` both doors with the switch on
  and off; a `demo_scenarios.rs` replay that consumes two same-difficulty
  questions in order; Studio Board section test; contract/fixtures if the key
  rides `play-state` (it should not need to).

## 3. Refusals surface globally

**Decided (operator):** keep the notice family; make addressed refusals
visible everywhere. Not a toast.

- Today `useHostCommand` routes a refusal with a `<path>:` message to that
  field only (`noticesAt`). The Load refusal for a Board problem therefore
  appears only on the Board page; on Roster nothing explains why Load did nothing.
- Change: an **error** notice whose `targetPath` is not on the current route
  also appears in the **collector** under the existing *"needs attention
  elsewhere"* line (P11.8, `inlineNotices`, `CHROME.elsewhereAt`) with a *Show*
  action that navigates to the place; the **status bar** counts it; and a
  refusal of `play_load` **opens the collector** so the operator sees it at the
  moment of the click. Inline marks on the Board page stay as they are.
- Extend `CHROME.elsewhereAt` with every recipe path a refusal can carry
  (`recipe.board`, `recipe.settings`, …) → *Game ▸ Board* etc., and make the
  *Show* action open that recipe's section.
- When a Board problem is fixed and the write succeeds, its notices clear (no
  stale "elsewhere" entries).
- Tests: a Studio test that refuses `play_load` from the Roster section and
  asserts the collector opens with the reason and a working *Show*.

## 4. Update notice

**Decided (operator):** on by default, with an off switch; opens GitHub.

- Host-side: `crates/app/src/update.rs`, one async check per launch, off the
  host lock, a few seconds after boot. `GET
  https://api.github.com/repos/aAndy03/question-game/releases/latest`
  (unauthenticated; `User-Agent` set; 5 s timeout). Compare `tag_name` (strip
  `v`) with the running version using semver; drafts/prereleases ignored.
- HTTP client: a small blocking/async client that passes the licence audit
  (e.g. `ureq` with rustls, or reuse what Tauri already pulls in). Builder's
  pick; justify in the commit.
- Result → an `info` notice `update.available` (*Version X is available* —
  actions: *Open release page*, *Not now*), shown in the collector, never
  blocking, never during a loaded Play (deferred until `play_unload`). Offline,
  rate-limited or any error: silent, logged at `debug`.
- Command `update_check { now_ms }` → `{ current, latest, url, newer }` for the
  Settings button; it reports errors to the button (*Couldn't reach GitHub*).
- Setting: global `updates.check_on_start` (default `true`), Settings ▸ About
  next to the version, plus *Check for updates*. Opening the page uses the
  opener the app already has for external links (or `tauri-plugin-opener`).
- `release:check` unchanged (the webview still fetches nothing). README and
  About mention that this is the app's only network call and how to turn it off.
- Tests: version comparison units; a parse test on a recorded GitHub response;
  the command with an injected fetch (the response is a parameter, not a trait).

## 5. What's new

- `CHANGELOG.md` at the repo root (Keep a Changelog style, one section per
  version, starting with 1.0.0, 1.0.1, 1.0.2), bundled into `dist/studio`
  the way the notices are, and read by Studio over `BASE_URL`.
- Global `app.last_seen_version`. *(Builder's call:)* an **absent** key is
  decided host-side from the same fact §6 uses: if the library **existed before
  this boot** (the database file was there when `open` began), the key reads as
  `1.0.1` — an upgrade from the last build that did not write it; on a genuinely
  new library it is set silently to the current version (first run has its own
  wizard). If the seen version is older than the running one, Studio shows a
  **What's new** dialog with the sections *newer than* the seen version
  (so a 1.0.1 operator sees 1.0.2 only), once; *Close* writes the current version.
- *(Builder's call:)* What's new **waits while a Play is loaded** (including one
  resumed at boot), using the same hold as the update notice, and appears after
  `play_unload`. It never opens over Control mid-show.
- Also reachable from Settings ▸ About (*What's new*).
- Tests: section selection between two versions; the dialog appears once.

## 6. Safe upgrade and backups

- **Backup before migrating.** In `CatalogService::open`, before `migrate`
  changes anything, if `user_version < head` **or** the stored app version
  differs from the running one, write `VACUUM INTO
  '<app data>/backups/questiongame-<old version>-<stamp>.sqlite3'` (consistent
  copy, WAL included). The backup is written and fsynced before the first
  migration step; if the backup fails, the app does **not** migrate and shows
  the boot failure message (data untouched beats data upgraded without a net).
- Keep the **5** newest backups; prune older ones after a successful open.
- Record the app version that last opened the library (a `meta` table row or
  the settings document) so a version change without a schema change is still
  backed up.
- A database newer than the app (`SchemaTooNew`, i.e. a downgrade) keeps
  today's refusal and the message names the backup folder.
- Settings ▸ Data shows the backups folder; *Remove generated data* removes it
  with the rest.
- Settings document: every key added in this release carries `serde(default)`;
  a test reads a 1.0.1 settings document and recipe row and gets the defaults.
- Tests: open a 1.0.1-schema fixture database → backup exists, migration
  applied, rows intact; backup failure → no migration; retention keeps 5.

## 7. Release and verification

- Version **1.0.2** in the three files.
- All suites: `npm run typecheck`, `lint`, `test`, `test:host`, `test:app`,
  `lint:host`, `lint:app`, `npm run build` (licence audit), `release:check`,
  `npm run release` (installer).
- **Real upgrade test on Windows:** install the published 1.0.1 installer,
  create data (seed Demo, edit a team, run a short Play), close, install 1.0.2
  over it, open → data intact, a backup in `backups/`, What's new shown once,
  update check silent (1.0.2 is latest once published; before, it reports 1.0.1
  is *not* newer).
- Release body and README: **"Install over your current version. Do not
  uninstall first — uninstalling with 'Delete the application data' ticked
  removes your library."** macOS: drag the new app over the old one.
- Push `main`, then tag `v1.0.2`; CI builds and publishes. macOS is CI's to
  build; its runtime check stays the operator's.
